# Contributing to FVTV

## Before opening a pull request

Create or link an issue that explains the deliverable, owner, source, due date, and completion evidence. For public-facing editorial work, include the source list, rights status, disclosure status, and fact-check state. For revenue work, include the approved offer, payment route, scope, and payment-before-work control.

## Pull-request requirements

Use a clear title such as `docs: add Purplepass activation checklist` or `ops: reconcile Groover review queue`. Keep one logical change per pull request. Link the issue with `Closes #number` only when the pull request fully completes it. Add screenshots or rendered previews for visual or public-facing changes.

A reviewer must check that the change does not expose private contact data, credentials, confidential agreements, unapproved rates, or unsupported claims. Legal documents are never edited casually in a content pull request. If a change creates a contract, spending, renewal, barter, or submission obligation, label it `approval-needed` and stop at a draft or checklist until explicit approval is recorded.

## Commit style

Use short imperative commits: `docs: add partner handoff`, `ops: log review deadline`, or `editorial: update issue 005 outline`. Do not include secrets or large binary assets. Reference private files by approved CRM or Drive location instead of committing them.

## Definition of done

A change is complete only when the linked issue includes evidence: a public URL, sent-message ID, uploaded file, payment receipt, partner confirmation, or documented closed/suppressed outcome. A draft alone is not completion.
